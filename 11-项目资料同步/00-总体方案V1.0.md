## 1. 项目背景、目标与"反模式对策矩阵"

### 1.1 背景

源项目复盘（PDF）记录了一个 120 万合同餐饮 AI 项目从签约到退款的全过程。其失败根因不是技术，而是工程治理：

1. **签约前未做数据资产评估**，三套异构系统（老ERP/新供应链/Excel补录）、命名不统一（"鸡翅膀/翅中/鸡翅（中）"）、单位混乱（克/斤/箱）；
2. **承诺了超出数据支撑的技术指标**（"误差15%以内"），而实际可达精度仅 65-75%；
3. **一次性承诺 6 个月全量交付**，无 Go/No-Go 节点；
4. **问题隐瞒 9 周**，客户信任崩塌于一次"8 公斤牛肉"的现场演示；
5. 演示**选择性展示**最优品类（樱桃数据），埋下信任炸弹。

复盘作者随后的重生项目证明了正确路径：**小切口（高价值食材当日用量监控）+ 已有数据 + 4周上线 + 承诺业务结果 + 58倍ROI**。

**本方案将上述 5 条教训全部转化为硬性设计约束**，逐条落实如下：

### 1.2 反模式对策矩阵（本项目必须全部规避）

| # | PDF 中的问题 | 本项目的硬性对策 | 落实位置 |
|---|---|---|---|
| P1 | 签约前无数据质量评估 | **Phase 0 即数据资产评估阶段**，交付《数据质量报告》并通过 Go/No-Go 评审后才进入开发 | §12.2 |
| P2 | 承诺技术指标（误差15%） | **只承诺业务结果**："试点门店高价值食材浪费率 3 个月内相对基线下降 ≥15%，未达标退还当期服务费"；技术指标仅作为内部验收参考并注明测量口径 | §1.3 |
| P3 | 6个月一次性交付 | 四阶段交付（Phase 0-3），**每阶段独立合同额与 Go/No-Go 评审**，任一阶段可无责终止 | §12 |

### 1.3 建设目标与业务承诺（承诺结果，不承诺指标）

**愿景**：为连锁餐饮企业构建一个可生长的"餐饮智能体平台"：以智能体（Agent）为核心交互范式，贯通"菜品—食材—采购—库存—浪费—预测—决策"全链路，并面向 C 端会员提供智能点餐/营销服务，平台具备支撑 **100 万注册用户** 的体系架构。

**分阶段业务承诺（写入合同模板）**：
- Phase 1 后：试点门店高价值食材**当日用量差异（理论vs实际）T+1 可视**，差异>15%自动预警；
- Phase 2 后：采购建议采纳率与浪费率基线对比**月度报告自动生成**，浪费率相对基线下降 ≥10%；
- Phase 3 后：浪费率相对基线下降 ≥15%（3个月滚动），否则退还当期服务费；
- 全程：**所有指标的计算口径（SQL/脚本）随报告交付，甲方可独立复核**。

### 1.4 规格口径（防止"100万人同时使用"的语义陷阱 —— 教训P2的直接应用）

"支撑100万人同时使用"必须定义清楚，否则就是 PDF 中"误差15%"式的超支撑承诺。本方案采用国标/行业通行口径：

| 口径 | 数值 | 依据 |
|---|---|---|
| 注册用户 | 100 万 | 建设目标 |
| 日活（DAU） | 10 万（10%） | 连锁餐饮 C 端会员行业基准 |
| 峰值同时在线会话 | 1~2 万（DAU 的 10~20%） | 互联网通行换算 |
| 峰值 API QPS（非LLM） | 5,000~10,000 | 峰值会话 × 平均请求速率 0.3~0.5 QPS/人 |
| 峰值 LLM 对话 QPS | 50~200 | 受 CPU 推理物理上限约束（见 §11.2），通过语义缓存+分级路由+排队保障 SLO |
| 数据存量 | 订单/流水 5 年 ≈ 1~2 TB（TiKV 600G 可支撑 2 年热数据，冷数据归档） | 容量推演 §11.4 |

> **诚实声明**：两台服务器（合计 80 核 / 256GB / 无GPU）物理上无法承载 100 万路**真实并发的 LLM 推理**。本方案通过"多级缓存拦截 80%+ 流量 + 意图分级路由 + 小模型优先 + 语义缓存 + 排队与降级"使 LLM 服务在上述口径下达标；若未来真出现百万级同时推理需求，需扩容 GPU 节点（架构已预留水平扩展点，见 §7.7）。**这是本方案与 PDF 失败项目的根本区别：把物理上限写在纸面上，而不是藏在演示后面。**

## 3. 先进性分析与技术选型（2026-10 前沿调研结论）

### 3.1 智能体协议：MCP + A2A（Linux Foundation 双标准）

2026 年现状：**MCP（模型上下文协议）连接"智能体↔工具/数据"，A2A（Agent2Agent 协议）连接"智能体↔智能体"**，二者互补，均已成为 Linux Foundation 托管标准，A2A 首年即获 150+ 组织支持。业界亦有声音认为 A2A 落地负担偏重（Credal 2026-03）。

**本项目选型**：
- 工具层**全面 MCP 化**：所有业务能力（查库存、下采购单、算差异）封装为 MCP Server，供任意智能体（自研/Dify/外部）标准化调用——这是 2026 年智能体互操作的事实标准；
- 智能体间通信**预留 A2A 接口**（AgentCard 声明 + JSON-RPC over HTTP），但 Phase 1-2 以进程内编排为主，**不过度设计**（吸取 A2A 落地负担教训）。

### 3.2 编排框架：LangGraph 模式（有状态图编排）

LangGraph 已成为低层级有状态多智能体编排的主流框架，生产实践集中在 Supervisor/分层/专家并行三类模式。**选型**：智能体运行时采用 **Python 3.12 + LangGraph**（自研核心智能体），Dify 保留作运营侧低代码补充。复杂决策链采用 Supervisor 模式 + 专家子图并行（点单/库存/采购专家并行 → 汇总评审）。

### 3.3 可观测性：OpenTelemetry GenAI 语义约定

OTel GenAI 语义约定 2026 年已生产可用（LLM调用/工具调用/MCP 均有标准 span 属性，Datadog 等已原生接入）。**选型**：全部服务接入 OTel → Prometheus/Loki（已有）；LLM 调用统一经 LiteLLM 网关埋点，质量评估（幻觉率/采纳率）以离线 Eval 平台（Ragas + 自建评审集）叠加。

### 3.4 API 层：GraphQL Federation

联邦网关 2026 三强：Apollo Router（Rust）、Hot Chocolate Fusion 16.5、Hive Router。**选型**：子图 = Spring for GraphQL（Java 21）；网关 = **Apollo Router Community（Rust）**，高吞吐、无 JVM 开销，适合本环境 CPU 预算。REST 保留给第三方回调/健康检查，内部东西向用 gRPC。

### 3.5 数据层：TiDB HTAP 读写分离

TiDB v8.5.8 兼容 MySQL 协议，多 TiDB Server 天然水平扩展，读写分离以"多 TiDB Server 实例 + 客户端读写分源"实现（详见 §7.4），无需额外中间件。

### 3.6 RAG 增强：混合检索 + 重排

Milvus 2.6（稠密）+ NebulaGraph（图检索：食材替代关系、菜品BOM图）+ BM25（TiDB全文）三路召回 → 已有 vector-reranker 重排 → qwen3-embedding 系列做向量化。

### 3.7 先进性对标总结

| 维度 | 业界2026前沿 | 本方案落地 |
|---|---|---|
| 智能体互操作 | MCP + A2A 双标准 | 工具层全 MCP；A2A 预留 |
| 编排 | LangGraph 有状态图 | LangGraph Supervisor + 专家并行 |
| 协议 | GraphQL Federation | Apollo Router + Spring GraphQL 子图 |
| 数据 | HTAP 读写分离 | TiDB 多Server读写分离 |
| 检索 | 混合检索+重排 | Milvus+图谱+BM25 → reranker |
| 可观测 | OTel GenAI 约定 | 全链路 OTel + Grafana/Loki |
| 工程 | DDD/TDD/BDD/SDD | 见 §10 |

## 4. TOGAF 业务架构

### 4.1 业务能力地图

```
连锁餐饮智能体平台
├── B1 门店运营域      排班/出品/领料扫码/损耗登记
├── B2 菜品与BOM域     菜品/配方/食材主数据(一品一码)/单位字典
├── B3 采购域          供应商/询比价/采购单/收货对账
├── B4 库存与浪费域    出入库/盘点/理论用量vs实际/浪费预警 ← Phase1核心
├── B5 需求预测域      分门店分SKU预测/置信度/数据依赖声明 ← Phase3
├── B6 会员营销域      C端会员/券/积分/智能点餐助手(百万用户入口)
├── B7 智能体门户域    会话/编排/工具治理/评测
└── B8 数据平台域      MDM/数据质量门禁/指标/血缘 ← 反P1/P7
```

### 4.2 核心业务流程（Phase 1 切口，源自 PDF 重生方案）

```
厨房领料扫码 → 当日实际用量自动归集
  → 与当日菜品销售×标准BOM 计算"理论用量"
  → 差异 = 实际 - 理论；差异率 > 15% 的门店×品类
  → 智能体归因分析(以次充好?收货缺斤?工艺损耗?) → 企业微信/APP预警采购主管
```

Phase 2 扩展到采购建议闭环，Phase 3 加入预测（数据成熟度达标后，且**预测结果永远带置信度与数据依赖清单**，缺数据时显式降级提示——反P6）。

4. **指标口径版本化**：所有业务指标（浪费率、差异率）SQL 脚本入 Git，口径变更走评审——指标可被甲方独立复核（反P5）。

## 7. TOGAF 技术架构

### 7.1 部署拓扑（K8S，新增 namespace：`fnb-prod` / `fnb-staging`）

```
用户/门店/C端 → ingress-nginx(扩至2副本) → Apollo Router(GraphQL网关×2)
  → 各领域服务 Pod（多副本，HPA按CPU自动扩缩）
智能体流量 → LiteLLM(已有) → Ollama(已有, qwen3:8b/14b优先)
数据面 → TiDB(已有) / Redis Cluster(已有) / Pulsar(已有) / Milvus(已有)
可观测 → OTel Collector → Prometheus/Grafana/Loki(已有)
```

### 7.2 多级缓存（L0-L4，全局命中率目标 ≥80%）

| 级 | 位置 | 内容 | TTL策略 |
|---|---|---|---|
| L0 | CDN/nginx proxy_cache | 静态资源、菜单海报 | 长，版本哈希 |
| L1 | 进程内 Caffeine | 菜品/BOM/单位字典（几乎不变） | 30min+事件失效 |
| L2 | Redis Cluster | 会话、门店库存快照、热点查询结果 | 秒级~分钟级 |
| L3 | **语义缓存（Milvus）** | LLM 问答对（问题向量→答案，相似度>0.92 直接命中） | 按业务域 |
| L4 | 数据库自身 | TiDB 缓冲池 | - |

写路径：先写 TiDB → 发领域事件 → 失效 L1/L2（延迟双删+版本号），保证最终一致。

### 7.3 读写分离（TiDB 多 Server）

- 新增 1 个 TiDB Server 副本（共3：`tidb-w`×1 专写、`tidb-r`×2 专读），K8S Service 拆分为 `tidb-write` / `tidb-read`；
- 应用侧双数据源（HikariCP），`@Transactional(readOnly=true)` 自动路由读源；MyBatis/Spring Data 天然支持；
- 报表/指标计算走只读源 + TiFlash 副本（v8.5 支持列存），避免影响交易；
- 缓存兜底：读 QPS 大头被 L1/L2 消化，DB 实际读压力预估 <1000 QPS。

### 7.4 消息与削峰（Pulsar）

- Topic 按领域事件划分（`fnb.inventory.consumed` 等），key=storeId 保证门店内有序；
- C 端秒杀/高峰下单 → Pulsar 队列削峰，消费端按 TiDB 写能力限速；
- 预警事件 → 独立 topic → 企业微信推送 + WebSocket 推送双通道。

### 7.5 网络与服务网格

东西向流量 Phase 1 用 K8S Service（简单可靠）；Istio 已装，Phase 2 可选启用金丝雀发布与 mTLS（不强依赖，避免复杂度前倾）。

### 7.6 GitOps 与 CI/CD

- 代码：Monorepo（`pnpm` + `Maven` + `uv` 多语言构建）或分仓（推荐 Monorepo，教学友好）；
- CI：构建→单测→契约测试→镜像→推 10.167.2.175:30500 仓库；
- CD：Kustomize/Helm 覆盖层 → `fnb-staging` 自动 → `fnb-prod` 手动审批（环境隔离）；
- 数据库变更：Flyway 版本化，禁止手工改库。

### 7.7 水平扩展预留

所有无状态服务可横扩；LLM 层预留"外部大模型 API 接入位"（LiteLLM 已支持多上游 failover）；若获 GPU，Ollama 换 GPU 镜像即插即用，架构零改动。

### 8.2 编排模式（LangGraph，Supervisor + 专家并行）

```
Supervisor(意图分类/路由, qwen3:8b)
 ├─→ 专家: 库存差异分析 ─┐
 ├─→ 专家: 采购比价     ─┼─→ Reviewer(合规/幻觉校验, 规则+小模型)

 └─→ 兜底: 人工工单
```

- 记忆：会话级（Redis）+ 长期画像（TiDB + Milvus 向量记忆）；
- 反思：Reviewer 节点校验数字一致性（LLM 输出的用量差值必须来自工具调用结果，不得编造——**数字类回答强制工具溯源**）。

### 8.3 工具层（MCP）

`mcp-fnb-tools` 暴露：`query_stock / compute_theoretical_usage / diff_analysis / create_alert / query_price / create_po_draft / search_knowledge` 等；统一经 `mcp-registry` 注册鉴权，工具调用全程 OTel 埋点（MCP span 标准属性）。

### 8.4 LLM 流量治理（CPU 推理物理约束下的 SLO 保障）

```
请求 → L2语义缓存(Milvus, 相似>0.92命中) →命中≈70%直接返回
      → 未命中 → 意图分级路由:
          简单FAQ/寒暄  → qwen3:4b  (16线程, 吞吐高)
          业务分析      → qwen3:14b (并发=2~4)
          复杂归因      → qwen2.5:32b(并发=1, 排队, P95≤30s)
      → 全链路排队(令牌桶)+熔断降级(返回引导语+工单)
```

实测口径将写入 Phase 0 POC 报告（CPU 推理吞吐实测 → 确定 SLO 承诺值，**先测后诺，反P2**）。

### 8.5 评测（Eval）

- 评审集：每智能体 ≥200 条真实场景用例（含边界/对抗样本），入库版本化；
- 自动指标：工具调用准确率、数字一致性（幻觉率）、延迟、成本（token/次）；
- 流程：每次 Prompt/模型/链路变更必须跑回归评测，报告进 Grafana 看板（**对甲方透明，反P4**）。

### 8.6 数据依赖声明机制（反 P6 的技术固化）

每个预测/分析类智能体在 `agent-manifest.yaml` 声明必需数据源；运行时前置检查数据新鲜度与完整性，不满足则：
```
输出 = { result: null, degraded: true, reason: "预订数据未接入(T+7)",
         fallback: "建议参考近7日均值", confidence: "LOW" }
```
**禁止静默给出看似正常的低置信结果**——"8公斤牛肉"事件的技术级绝杀。

## 10. 软件工程流程（DDD+TDD+BDD+SDD+CI/CD）

### 10.1 SDD（规格驱动，一切先有规格）

顺序：**业务事件风暴 → 领域模型（DDD）→ API契约（GraphQL Schema / OpenAPI / MCP tool schema）→ 验收标准（Gherkin）→ 实现**。契约文件入库 `contracts/` 目录，前后端/智能体并行开发互不阻塞，契约测试（Pact/schemathesis）进 CI 门禁。

### 10.2 TDD

- 领域层单测覆盖率 ≥80%（Jacoco 门禁）；
- 测试金字塔：单元（JUnit5/Pytest）→ 组件（Testcontainers 连真实 TiDB/Redis/Pulsar）→ 契约 → E2E；
- 缺陷回归：每个 bug 先写失败用例再修复。

### 10.3 BDD

- 用户故事以 Gherkin 编写，例：
```gherkin
场景: 高价值食材用量差异预警
  假如 2号店 今日售出"黑椒牛柳"58份 且 标准BOM牛肉用量为150克/份
  当 厨房领料扫码登记牛肉领用共12.8公斤
  那么 差异率为 -3.0% 不触发预警
  当 领料登记为6.0公斤 且 差异率47.1%超过阈值15%
  那么 系统T+1生成预警并推送采购主管 且 差异明细可溯源到每一笔单据
```
- Gauge/Cucumber 执行，测试报告附验收文档（可追溯矩阵：需求↔用例↔代码）。

### 10.4 DDD 战术规范

聚合划分（如 `PurchaseOrder` 聚合含明细，领料单 `StockMovement` 为独立聚合）、值对象（`Quantity{value, unit}` 强类型单位）、领域事件命名过去式、CQRS 仅在指标/报表读模型使用（不滥用于全系统）。

### 10.5 分支与版本

- 分支：trunk-based + 短生命周期feature分支；语义化版本；Conventional Commits；
- 每周发布列车，staging 全量回归 → prod 金丝雀（v1/v2 双Deployment切流）。

### 10.6 透明交付制度（反 P4/P5 的制度化，写入SOW）

1. **双周演示例会**：永远现场随机抽门店/品类演示，禁止预选"樱桃数据"；
2. **周报自动化**：Grafana 交付看板（进度/缺陷/风险红黄绿灯）+ 数据质量看板公开链接；
3. **风险台账**：任何红/黄风险 24h 内书面知会甲方；
4. **指标口径全公开**：所有对外承诺指标的计算 SQL 随报告交付。

**No-Go 标准示例**：关键字段缺失率>20% 且无补充方案；或高价值食材无BOM可建立。此时止步，仅收评估阶段费用（对应 PDF 教训一"评估阶段收费"模式）。

### 12.2 Phase 1：MVP（6周）——单一切口，跑通价值

范围：`svc-recipe`、`svc-inventory`、`svc-agent-portal`、`agent-runtime`（差异分析Agent）、`mcp-fnb-tools`、`svc-mdm`+质量门禁、`web-admin`+`h5-store`（扫码）；3家试点门店。
Go 标准：差异计算准确率（对账人工抽检30笔全对）、预警T+1送达率≥99%、试点店长可用性评分≥4/5。

### 12.3 Phase 2：采购闭环+模拟推广（8周）

范围：`svc-procurement`、`svc-store`、采购建议Agent（人在环）、32门店模拟数据、全链路压测（第一轮）。
Go 标准：浪费率相对基线降≥10%（月度自动报告）、采购建议采纳率≥30%。

### 12.4 Phase 3：预测+C端+百万压测（9周）

范围：`svc-forecast`（带数据依赖声明与置信度）、`svc-member`+小程序点餐助手、语义缓存调优、百万用户全链路压测（§11.5 四场景达标）。
Go 标准：§1.3 业务承诺达成（浪费率降≥15% 或退费条款触发）、压测四场景全过、SLO 燃烧率<2×。

### 12.5 团队与工时（建议）

架构师1（兼）、后端2、前端1、算法/Agent 1、测试1、DevOps 0.5；甲方配合：业务专家0.5、门店试点3家、数据接口人0.5。
