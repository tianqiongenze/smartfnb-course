### 集群中两处异常的根因定位与修复（2026-10-30 追加；均早于本轮、与本项目无关）

**异常一：`monitoring/kube-prometheus-stack-operator` CrashLoopBackOff（修复前 289 次重启）**

根因链（两层，均有实测）：

| 层 | 机制 | 证据 |
|---|---|---|
| 直接原因 | 存活探针预算容不下启动耗时：`livenessProbe=/healthz(HTTPS:10250) timeoutSeconds=1 periodSeconds=10 failureThreshold=3`，**无 `startupProbe`、无 `initialDelaySeconds`** | `kubectl describe pod` 事件：`Liveness probe failed: Get "https://192.168.194.141:10250/healthz": net/http: request canceled (Client.Timeout exceeded while awaiting headers)`；`Readiness probe failed: ... connection refused` |
| 根本原因 | 容器 `resources` 为空 → **QoS=BestEffort** → 该节点上 `cpu.shares=2`（同节点 BestEffort 容器实测值），被同节点 `ai-platform/ollama-worker`（实测 30.5 核 / 33 GiB）压制；启动与 handler 被饥饿 | `/sys/fs/cgroup/cpu/cpu.shares` = **2**；`cgroup` 路径含 `kubepods-besteffort.slice`；`cpu.stat` `nr_throttled=0`（非配额节流，是份额饥饿）；`kubectl top node` worker1 32.9 核 51% / 92 GiB 71% |
| 饥饿量化 | 同镜像同参数下，启动到 `starting secure server` 耗时 **+21s**（BestEffort/worker1）对比 **+0.07s**（Burstable/master），差约 300 倍 | 旧 Pod 日志 `startedAt=03:29:21Z` → `starting secure server ts=03:29:41.935Z`；新 Pod `startedAt=05:26:47Z` → `ts=05:26:47.287Z` |
| 探针实测 | 55 次采样：200 的耗时分布 0.006–5.133s，其中 **9 次 >1s**（即探针判失败）；另有 23 次 `connection refused` 出现在 uptime **+2s…+89s**（监听口在 89 秒仍未打开）；每个崩溃周期内 `code=000` 占多数 | 采样为会话临时件（`/tmp/healthz_watch.sh`，未入库）；汇总数字已抄录于此。**口径警告见下**：其中「200 的耗时」不可信，「connection refused」仍可信 |
| 杀死后果 | SIGTERM 打到 informer 同步中，v0.90.1 把「未同步完」当致命错误退出 1 → 5m backoff → 无限循环 | 日志 `received SIGTERM, exiting gracefully...` → `unhandled error received. Exiting... err="failed to sync cache for Prometheus informer"`，`exitCode=1` |

时间线（排除"清单变更导致"）：Deployment 的 RS `768867cc4f` 创建于 **2026-05-20T00:44:36Z**、`revision=1`、镜像与探针参数在这 5 个月里未变；旧 Pod 年龄 19d（≈2026-10-11，即节点重启后重建）；operator 最后一次成功改写 Prometheus STS 是 **2026-10-10T03:51:24Z**。所以故障起点与 10-10/10-11 的运行环境变化（worker1 重启 + 共存负载变重）一致，而不是任何配置变更。旧 Pod 已随本次滚动删除，其 `creationTimestamp` 无法再复核，此处依据为删除前记录的 `AGE 19d`。

修复（已执行）：给该容器 `requests {cpu:200m, memory:256Mi}` + `limits {cpu:1, memory:512Mi}`（脱离 BestEffort，实测 `cpu.shares` 2 → **204**），并把探针改为 `timeoutSeconds=5 periodSeconds=15 failureThreshold=4` + 新增 `startupProbe(periodSeconds=5, failureThreshold=60 → 最长 300s 启动窗口)`。`limits.cpu=1` 未引入节流：容器内 `cpu.stat` 两次读数 `nr_periods 2116 → 4631`（CFS 周期数在涨，说明容器活着且被调度），而 `nr_throttled` 始终为 **1**、`throttled_time` 始终为 **45.7 ms** —— 20 分钟内新增节流 **0 次 / 0 ns**。长跑复核（Pod 起于 `2026-10-30T05:26:34Z`）：`restarts=0`、`ready=true`、`node=k8s-master`、`qos=Burstable`、`cpu.shares=204`。

**不能证明归因权重**：`resources` 与探针参数在同一次 strategic patch 里一起下发，未做单变量拆分实验，因此无法证明"只加 requests 不改探针"或"只改探针不加 requests"各自能否独立消除 CrashLoop。现网实测给出的是倾向性线索：端点真实耗时约 5 ms，旧的 `timeoutSeconds=1` 在健康服务端上本可通过，所以**决定性因素更可能是 requests/落点**；而 `startupProbe(300s 窗口)` 是针对"+21s 启动"这一形态的保险 —— 若将来该 Pod 再被调度回 worker1，仅靠 1s 探针仍会复发。

**防复现（未执行，属平台侧治理）**：`kube-prometheus-stack` 的 operator 容器与 node-exporter、grafana 一样 `resources` 为空 → 一律 BestEffort → 在 cgroup v1 上得 `cpu.shares=2`。这是 Chart 默认值与该集群 worker1 超重负载叠加的系统性坑，任何一次落到 worker1 的 BestEffort 组件都会重演。建议在 Helm values 里为 chart 全部组件显式设 `resources.requests`，而不是逐个手工 patch。手工 patch 存在被下一次 `helm upgrade` 回退的风险——**该风险按 Helm 三方合并语义推断，未实测**（在本集群跑 `helm upgrade` 会扰动其他项目，已回避），且该 Deployment 由 `managedBy=Helm` 持有、`release=kube-prometheus-stack`，一旦有人升级该 release 就会暴露。

#### 撤回：修复后「`/healthz` 仍有偶发秒级尖刺（最长 5.95s）」是我的测量工具造成的假信号

修复后我一度报告"残留尖刺未被解释"。用 Prometheus 侧独立抓取数据 + 同窗双客户端对照复核后，**该结论作废**——尖刺来自测量路径，不是 operator。

| 观测源 | 路径 | 旧 Pod（worker1/BestEffort） | 新 Pod（master/Burstable） |
|---|---|---|---|
| 我的采样器 | `kubectl exec` 进 **grafana Pod** 再起 `curl`，而 grafana 实测 `node=k8s-worker1 qos=BestEffort cpu.shares=2`（无 requests/limits） | — | 同一采样器三轮：门禁 v3 最大 3128ms、门禁 v4 最大 3878ms、同窗对照最大 **5950ms** |
| Prometheus（权威） | `job="kube-prometheus-stack-operator"`，`port=https` = **containerPort 10250**、`scheme=https`，与 `/healthz` **同一个 TLS HTTP server、同一个端口** | `up=1` **177/649（27.3%）**；`scrape_duration_seconds` 650 采样中 **191 次 >1s**，最大 **10.016s**（撞抓取超时） | `up=1` **72/72（100%）**；72 采样最大 **0.023s**，>0.5s **0 次** |

机制：`time_total` 是 curl 进程内的墙上时间，curl 本身被调度在 worker1 的 BestEffort 容器里 → 客户端被份额饥饿，与服务端无关。这与异常一根因（BestEffort 饥饿）是同一族，连我的探针都中招。旁证：`connection refused` 由内核在无人监听时直接返回，不经服务端应用，因此该项不受此污染，仍成立。

同窗对照实验（唯一变量 = 客户端落点/QoS，二者同时交替各打 8 次同一个 `https://192.168.235.235:10250/healthz`）：

| 客户端 | 落点 / QoS / 实测 `cpu.shares` | 8 次 `time_total` |
|---|---|---|
| grafana Pod（我原采样器） | k8s-worker1 / BestEffort / **shares=2** | 200 全部成功，但 **0.45 / 1.22 / 1.52 / 1.88 / 2.00 / 2.72 / 5.11 / 5.95 s** |
| `ai-platform/llm-proxy-master` | k8s-master / Burstable / shares=512 | 200 全部成功，**0.0046–0.0067 s**（12 次独立采样同为 4.6–6.1 ms） |
| Prometheus（权威第三方） | worker1 / Burstable(req cpu=500m) | 同端口同 server 抓取 72 次，最大 **0.023 s**，>0.5 s **0 次** |

三个仪器、同一服务端，只有客户端饥饿程度不同的那一台出现秒级尖刺 → 归因确定：**尖刺属于测量端，operator 实际约 5 ms**。旧采样器 5.95s > 新预算 5000ms 也正好解释了门禁 A2 里那 3 次"失败"。

**不能证明**：以上 20 次手工采样 + 72 次抓取全部落在空闲期，未覆盖大量 ServiceMonitor/Rule 并发 reconcile 的时刻，因此不能证明 `/healthz` 在高负载下永不超 1s；能证明的是"修复后残留尖刺"不是 operator 变慢。方法教训：**测延迟的容器不能与被测对象同处饥饿节点（尤其不能用 BestEffort 客户端），优先用 Prometheus 侧的 `scrape_duration_seconds` / `up` 而非自造采样器。**


**异常二：`kube-system/docker-registry-master` Pod Pending 7d21h**

根因：该 Deployment `hostNetwork=true` + `hostPort 5000` + `nodeSelector: kubernetes.io/hostname=k8s-master`，副本 1，策略 `RollingUpdate(maxSurge 25%→1, maxUnavailable 25%→0)`。2026-10-11 18:32:40(+0800) 的一次 `kubectl rollout restart` 产生 revision 2 的 surge Pod，它要在 master 上绑 5000，而 5000 仍被 revision 1 的在跑 Pod 持有；Deployment 又要等新 Pod Ready 才删旧 Pod → **永久性 hostPort 死锁**，与被重启的模板内容无关（两模板仅 `restartedAt` 注解不同）。

| 证据 | 值 |
|---|---|
| 调度失败原因（7013 次） | `0/2 nodes are available: 1 node(s) didn't have free ports for the requested pod ports, 1 node(s) didn't match Pod's node affinity/selector` |
| 在跑 Pod | `docker-registry-master-79fff4756d-gtkgd`，`podIP=hostIP=10.167.2.175`，`hostNetwork=true`，节点 k8s-master |
| Deployment 状态 | `replicas=2 ready=1 unavailable=1`，条件 `Progressing=False reason=ProgressDeadlineExceeded`（`ReplicaSet "docker-registry-master-656c4cb8c7" has timed out progressing`，2026-10-22T07:01:41Z） |
| 两个 RS 模板差异 | 仅 `kubectl.kubernetes.io/restartedAt=2026-10-11T18:32:40+08:00`；nodeSelector/hostPath/resources 完全一致 |

修复（已执行）：`rollout undo --to-revision=1`（模板回到与在跑 Pod 完全一致 → 卡死 RS 缩到 0，**Pod 零重启零中断**）；并把 `docker-registry-master` 与 `docker-registry` 的策略都改为 **`Recreate`** 防复现 —— `docker-registry`（worker1，100 个仓库那台）同样是 `hostNetwork + hostPort 5000` 且**没有 nodeSelector**，两者互抢同一宿主机端口，任何一次 `rollout restart` 都会掉进同一个死锁。

## 四、有意不清退的两项及其理由

### 本地镜像仓库（`fnb/*` 110 tag + `perf/*` 7 tag）

1. 删 tag 只删 manifest，**blob 不释放**；真正释放需对共享 registry 执行 `registry garbage-collect`，那是对公共中间件的写操作，违反"不动公共依赖"约束；

3. 镜像是重建的前提，删掉需重新构建 15 个镜像。

### 共享 Ollama 中的 `hermes3:8b`（4.7 GB）

归属证据：`ollama list` 显示其 MODIFIED「4 days ago」，与本项目 R10 实验 `smartfnb/tools/llm-bench/hermes_vs_qwen.py`（`BASE=http://10.167.2.176:30086`，经核实 = `ai-platform/ollama-worker-nodeport`）时间吻合。

不删的理由：模型位于 **共享** 模型库（`/home/k8s-data/ollama`，170 GB / 25 模型，多项目共用）。已检索 ai-platform / dify-plus / dataagent-prod / pdm-prod / education-platform 的 deploy+cm 未见 hermes 引用，但 **局限**：Dify 的模型供应商配置存于 postgres，未覆盖检索，不能证明无引用。

## 七、本轮暴露的工具缺陷（待修）

**`smartfnb/tools/redis-warmup/warmup.py` 的 wipe 在 Redis Cluster 下静默失效**

- `warmup.py:26` 用 `scan(match="fnb:*", count=2000)` 取键，`warmup.py:28` 以 `client.delete(*keys)` 一次性提交最多 2000 个键；
- Redis Cluster 对跨 hash slot 的多键命令返回 `CROSSSLOT Keys in request don't hash to the same slot`；
- 异常在 `warmup.py:30-31` 被捕获后仅打印 `wipe node skip`，**整个主节点的清理被放弃**，计数器 `n` 保持 0；
- 但 `warmup.py:129` 仍输出 `WARMUP DONE ... errors 0` → **假绿灯**：88,161 条写入全部成功，而"先清旧键"一条都没生效；
- 后果：重复跑 warmup 会累积陈旧 `fnb:*` 键而非替换。实测成立——本轮清退前集群内 `fnb:*` 键 TTL 统一为 2,245,049 s（≈26 天），即 10-26 那次 warmup 写入的键从未被后续运行清理；
- 修法：改逐键 `unlink`（本轮清退即采用此法，51,007 条命令全部返回 1），或按 slot 分组后批量提交。

> 口径存疑（**未定论，不作为结论**）：`warmup.py:129` 打印的 `cluster dbsize=17,296`，与本轮实测三主节点各约 17,000（合计 51,106）不一致。若 `RedisCluster.dbsize()` 为跨节点求和则 17,296 无法解释；若实际只取单节点则标签「cluster」为误导。未验证到确切原因。

## 十、注意事项（历史教训沿用 + 本轮新增）

1. **永远不用 `kubectl set env` 改 Deployment**（会触发重建回滚镜像）；改配置一律 `apply -f` 或 `set image`；
2. `set image` 后须用 `imageID` 核对双节点 digest 一致（曾出现 worker 缓存旧 digest 导致修复未生效）；
3. **【新增红线】`ollama-fnb` 与共享 `ai-platform/ollama-worker` 共用 hostPath `/home/k8s-data/ollama`（worker1，170 GB）**——任何"清理模型腾空间"的操作都会波及他项目，禁止执行；
4. **【新增】本地仓库有两个后端**：`docker-registry`（NodePort 30500 → worker1 pod，`/var/lib/registry` 64.7 GiB，真库）与 `docker-registry-master`（仅 ClusterIP，`/var/lib/registry-master` 148.5 MiB，近乎空，且其 pod 已 Pending 7d19h）。`10.100.135.132:5000` 与 `10.167.2.175:30500` 指向同一 service，历史上"重注册"并未改变存储位置；
5. **【新增】对共享 Redis 集群做批量删键必须逐键提交**，否则 CROSSSLOT 会静默丢操作（§七）；
6. **【新增】现网改动必须回写清单**：本轮发现 5 处镜像漂移，均是历史上用 `set image` 直改现网而未回写 `deploy/*.yaml` 所致——这正是"一键恢复会回退"的根因；
7. **【新增】文档声明必须带取证方式**：本版每行状态均标注实测命令。凡探针自身不可信（如 §九的 TiKV 容量、§八的五条假信号），一律显式撤回并标注"不能证明"，不以推断补位。
